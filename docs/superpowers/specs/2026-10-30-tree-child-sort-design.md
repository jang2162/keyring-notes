# 파일 트리 하위 노트 정렬 — 설계

## 의도

파일 트리에서 노트마다 바로 아래 하위 노트를 어떤 순서로 보일지 고른다. 지금은 모든 노드가 이름순(`buildNodeTree`)이고, 데일리 폴더만 동기화되는 화면 설정 `prefs.dailySortDesc` 로 이름 역순이 된다. 사용자는 노트마다 이름순·수정순·조회순·커스텀 중 하나를 고르고, 커스텀이면 끌어 놓아 순서를 직접 정하고 싶어 한다.

같은 볼트를 쓰면 기기가 달라도 같은 순서로 보여야 한다(사용자 결정).

## 목표

- 노트 하나에 「하위 노트 정렬」 을 **이름순·수정순·조회순·커스텀** 중 하나로 정한다. 그 노트의 **바로 아래 하위 노트**에만 적용된다.
- 워크스페이스 바로 아래 노트들의 정렬도 같은 네 가지로 정한다.
- 정렬 선택과 커스텀 순서는 볼트에 남고 동기화된다. 같은 볼트면 모든 기기에서 같다.
- 커스텀 순서는 트리에서 하위 노트를 **행 사이에 끌어 놓아** 정하고, 끌기 어려운 환경을 위해 메뉴 「위로」·「아래로」 와 단축키도 둔다.

## 비목표

- 정렬 방향 뒤집기(최근 것이 아래 등). 방향은 아래 「정렬 규칙」 으로 고정한다.
- 정렬 물려받기. 정하지 않은 노트는 늘 이름순이다(사용자 결정).
- 「가장 많이 연 순서」. 조회순은 최근에 연 순서다(사용자 결정).
- 워크스페이스 사이의 순서. 이미 `keyring-settings.md` 의 `workspaceOrder` 가 맡는다.
- 첨부 목록 정렬.
- 기존 노트에 수정 시각을 한꺼번에 채워 넣는 것(사용자 결정 — 아래 「시각이 없는 노트」).
- 위젯의 `modified` 열(`widget.ts` 가 `doc.mtime` 으로 계산)을 새 수정 시각으로 바꾸는 것. 같은 낱말이 두 근거를 갖게 되므로 후속으로 따로 정한다.

## 반목표 (기술적으로 돌아가도 실패인 것)

- **노트를 열기만 했는데 볼트 파일이 바뀐다.** 조회 기록을 볼트에 쓰면 열 때마다 동기화·서버 커밋이 생긴다.
- **순서를 한 번 바꿨는데 여러 파일이 바뀐다.** 처음 커스텀으로 바꿀 때의 한 번(아래 「처음 커스텀으로 바꿀 때」)을 빼고는 옮긴 노트 한 개만 바뀌어야 한다. 그래야 기기 둘이 서로 다른 노트를 옮겨도 충돌하지 않는다.
- **같은 노트를 동기화할 때마다 다시 올린다.** 서버가 받은 내용의 시각을 다시 덮어쓰면 로컬 해시와 서버 해시가 계속 어긋나 끝없이 다시 올리고 커밋이 쌓인다(아래 「적는 규칙」).
- **지금은 자동으로 합쳐지던 동시 편집이 충돌 사본이 된다.** 두 기기가 같은 노트의 다른 문단을 고치면 양쪽이 시각 줄을 바꾼다(아래 「병합」).
- **같은 볼트인데 기기마다 수정순이 다르다** — 조회순과 「시각이 없는 노트」 만 예외다.

## 결정 (사용자)

| 항목 | 결정 |
| --- | --- |
| 저장 범위 | 볼트에 둔다. 같은 볼트면 기기가 달라도 같은 설정 |
| 정하지 않은 노트 | 이름순(물려받지 않음) |
| 조회순의 뜻 | 가장 최근에 연 순서 |
| 수정순의 「수정」 | 본문 편집·이름 바꾸기·옮기기·속성(아이콘·순서 등) 변경 모두 |
| 링크 고쳐 쓰기 | 이름 바꾸기·옮기기로 다른 노트의 링크를 앱이 고치면, 그 다른 노트들도 수정으로 친다 |
| 시각이 없는 기존 노트 | 파일 시각으로 대신하고, 로컬 모드 기기끼리 어긋나는 것을 받아들인다. 한꺼번에 채워 넣지 않는다 |
| 순서 바꾸기 | 부모가 커스텀일 때만 행 사이 끌어 놓기·위로/아래로가 된다 |
| 워크스페이스 맨 위의 정렬 | 파일 보기 둘째 줄의 「더 보기」 메뉴에서 고른다 |
| 정렬 방식을 둘 곳 | 부모 노트 프런트매터 |
| 커스텀 순서를 둘 곳 | 하위 노트마다 프런트매터의 rank 값 |
| 수정 시각의 근거 | 앱이 노트 프런트매터에 적는 시각 |

## 접근(검토한 것과 고른 것)

**정렬 방식·커스텀 순서를 어디에 둘까**

- A. 부모 노트 프런트매터에 정렬 방식과 하위 이름 목록 — 노드를 옮기면 따라가지만, 순서를 바꿀 때마다 부모 파일 하나가 바뀌고 하위 노트 이름을 바꾸면 부모 목록도 고쳐야 한다.
- B. `keyring-settings.md` 한 곳에 노드 경로별로 — 노트는 깨끗하지만 모든 순서가 한 파일에 모여, 기기 둘이 서로 다른 노트의 순서를 바꿔도 같은 파일이 충돌하고 노드를 옮길 때마다 경로를 고쳐야 한다.
- C. 하위 노트마다 rank 값 — 순서를 바꿀 때 옮긴 노트 하나만 바뀐다.
- **고른 것: 정렬 방식은 A(부모), 순서는 C(하위 rank).** 커스텀에서 이름순으로 바꿨다 돌아와도 rank 가 남아 순서가 되살아난다.

**수정 시각의 근거**

- 가. 앱이 바뀔 때마다 노트에 시각을 적는다 — 내용과 함께 동기화되어 모든 기기가 같은 값을 본다. 다른 편집기로 고치면 갱신되지 않는다.
- 나. 서버 git 기록 + 로컬 파일 시각 — 노트 내용은 그대로지만 모드마다 근거가 달라 같은 볼트에서도 순서가 어긋나고, 파일 시스템은 이름 바꾸기·옮기기에 시각을 바꾸지 않으며, 동기화로 받은 파일은 받은 시각이 찍힌다.
- **고른 것: 가.**

## 데이터

프런트매터 필드 이름은 내 결정이다.

| 자리 | 필드 | 값 | 없으면 |
| --- | --- | --- | --- |
| 부모 노트 | `sort` | `name` · `modified` · `viewed` · `custom` | 이름순 |
| 하위 노트 | `rank` | 정렬 가능한 글자 키(아래) | rank 없는 노트로 친다 |
| 모든 노트 | `edited` | ISO 8601 시각(UTC) | 파일 시각으로 대신한다(아래 「시각이 없는 노트」) |

- **수정 시각 필드는 `updated` 가 아니라 `edited` 다(내 결정).** 위키 스키마(`wiki.ts`)가 에이전트에게 `updated` 에 「내용을 마지막으로 손본 날짜」 를 쓰게 하고, 오래된 페이지 검사(`analysis.ts`)가 그 값을 읽는다. 같은 필드를 쓰면 순서만 바꿔도 오래된 위키 페이지가 새것으로 보인다. `modified` 는 위젯이 계산하는 내장 필드(`frontmatter.ts` 의 `BUILTIN_FIELDS`)라 쓸 수 없다.
- 트리 응답은 지금 `icon` 을 프런트매터에서 붙여 보낸다 — 서버는 `ScopedVault.withIcons`, 로컬은 `LocalVault.tree` 가 `meta.frontmatter.icon` 을 읽는다. `sort`·`rank`·`edited` 도 같은 길로 `TreeNode` 에 실어 `VaultNode` 까지 가져온다.
- 서버 모드 트리에는 지금 시각이 없다. `edited` 가 없는 노트의 대체값으로 서버 색인의 파일 시각도 트리에 함께 싣는다.

## 정렬 규칙

부모의 `sort` 로 바로 아래 하위 노트를 정렬한다. 모든 규칙의 마지막 동점 처리는 이름순(`localeCompare(…, "ko")`, 지금과 같은 비교)이다 — 어느 기기에서나 같은 순서가 나와야 한다.

| `sort` | 순서 |
| --- | --- |
| 없음·`name` | 이름순. 단 데일리 폴더는 지금처럼 `prefs.dailySortDesc` 를 따른다(정렬을 따로 정하지 않았을 때만) |
| `modified` | `edited`(없으면 파일 시각)가 최근인 것이 위 |
| `viewed` | 이 기기에서 최근에 연 것이 위. 한 번도 연 적 없는 노트는 그 뒤에 이름순 |
| `custom` | rank 가 있는 노트를 rank 오름차순으로, 그 뒤에 rank 없는 노트를 이름순 |

노트 없는 폴더 노드(하위 노트)는 시각·rank 를 가질 수 없다. 수정순에서는 시각 없음으로 맨 뒤(이름순), 커스텀에서는 rank 없음으로 친다(노트가 생기는 때는 아래 「rank 가 어긋날 때」).

## 정렬 고르기

- **노트:** 트리에서 노트 행의 메뉴에 「하위 노트 정렬」 을 두고 네 가지 중 고른다. 지금 값에 체크 표시.
- **워크스페이스 바로 아래:** 워크스페이스 하나를 보는 동안에는 트리에 워크스페이스 행이 없다(`docs/ops/ux.md` 「상단 UI 통합」 절 — 전환기가 트리의 루트 표시를 겸한다). 그래서 파일 보기 둘째 줄의 「더 보기」 메뉴에 「노트 정렬」 을 두어 지금 워크스페이스의 바로 아래 노트들의 정렬을 고른다(사용자 결정). 모든 워크스페이스 보기에서는 워크스페이스 행의 메뉴에도 「하위 노트 정렬」 이 있다.
- 고르면 부모 노트 프런트매터의 `sort` 를 바꾼다(이름순을 고르면 필드를 지운다). 워크스페이스는 `<워크스페이스>.md` 에 적는다 — 화면에서 열지 않는 내부 표식 파일이지만 아이콘도 이미 그 프런트매터에서 읽는다(같은 절).
- **노트 없는 폴더 노드에서 이름순이 아닌 것을 고르면 그 노드의 노트를 빈 노트로 만들고 적는다.** 트리는 이미 노트 없는 노드를 「쓰면 노트가 생기는 빈 노드」 로 다룬다(`openNode`).

## 커스텀 순서

**rank 값.** 두 값 사이에 언제나 새 값을 만들 수 있는 글자 키(fractional indexing)를 쓴다. 넣을 때 다른 노트의 rank 를 다시 매기지 않는다. 구현(라이브러리를 쓸지 직접 쓸지)은 빌더 몫이다.

**처음 커스텀으로 바꿀 때.** 하위 노트에 rank 가 하나도 없으면 지금 보이는 이름순 그대로 **노트가 있는** 하위 노트에 rank 를 적는다. 노트 없는 폴더 노드에는 노트를 만들지 않는다 — 데일리 폴더의 연·월 묶음처럼 빈 노트가 한꺼번에 생기는 것을 막기 위해서다(내 결정). 서버 모드에서는 한 커밋으로 묶는다(`batch`). rank 가 이미 있으면(커스텀이었다가 다른 정렬로 바꿨던 경우) 아무것도 적지 않고 남은 rank 로 보인다. 처음 적을 때 그 하위 노트들의 `edited` 가 한 번 바뀐다 — 「순서 변경도 수정」 이라는 결정에서 오는 대가다.

**순서 바꾸기는 부모가 커스텀일 때만 된다.**

- 끌어 놓기: 행의 위쪽·아래쪽 가장자리에 놓으면 그 사이에 삽입선을 보이고 순서만 바꾼다. 행 가운데에 놓으면 지금처럼 그 노트 안으로 옮긴다(`Tree` 의 `drop` → `actions.move`). 가장자리의 폭은 빌더 몫이다. 부모가 커스텀이 아니면 가장자리 판정을 하지 않고 지금 동작 그대로다.
- 같은 부모 안에서만 순서를 바꾼다. 다른 부모의 행 사이에 놓으면 그 부모 안으로 옮기는 것으로 친다(그 부모가 커스텀이면 놓은 자리에 rank 를 매겨도 된다 — 빌더 몫).
- 메뉴 「위로」·「아래로」 와 단축키: 같은 부모 안에서 한 칸 옮긴다. 키는 빌더가 `shortcuts.ts` 의 기존 키와 겹치지 않게 고른다.
- 순서를 바꾸면 **옮긴 노트 하나**의 `rank` 만 바뀐다(그 노트의 `edited` 도). 위·아래 이웃이 rank 없는 노트라 사이 값을 만들 수 없으면, 옮긴 자리까지의 rank 없는 노트에 rank 를 함께 적는다 — 이것이 한 번에 여러 파일이 바뀌는 유일한 경우다.

**rank 가 어긋날 때.**

- 같은 rank 가 둘이면(두 기기가 같은 자리에 동시에 넣은 경우) 이름순으로 가른다.
- 노트를 다른 부모 안으로 옮기면 그 노트의 rank 를 지운다 → 새 부모에서 rank 없는 노트로 맨 뒤에 붙는다.
- 커스텀 부모 아래의 노트 없는 폴더 노드는 **사용자가 그 노드의 순서를 처음 바꿀 때** 그 노드의 노트를 만들고 rank 를 적는다.

## 수정 시각 `edited`

**적는 때.** 앱이 노트 파일의 내용을 바꾸는 모든 쓰기에서 그 노트의 `edited` 를 지금 시각으로 적는다. 다음이 모두 든다:

- 저장(편집기 자동 저장), 할 일 체크
- 이름 바꾸기·옮기기(노드 이동으로 함께 옮겨지는 하위 노트 포함)
- 이름 바꾸기·옮기기로 **다른 노트의 링크를 고쳐 쓴 것**(사용자 결정)
- 속성 변경(아이콘·`sort`·`rank` 등)
- 되돌리기·휴지통 되살리기·데일리 형식 옮기기

노트를 연 것만으로는 적지 않는다. `keyring-settings.md` 는 트리의 노트가 아니므로 적지 않는다.

**적는 자리는 쓰기 계층이다** — 로컬 모드는 core 의 `LocalVault.apply`(그 기기에서 일어난 변경, `source: "local"` 일 때만), 서버 모드는 서버의 `Vault.batch`. 앱 화면만이 아니라 API·에이전트로 쓰는 것도 같은 규칙을 따르게 하기 위해서다(내 결정). 동기화로 받은 변경(`"sync"`)과 앱 밖의 변경(`"external"`)에는 적지 않는다.

**동기화 기기의 쓰기에는 서버가 적지 않는다(내 결정).** 로컬 모드의 동기화는 바뀐 노트를 서버의 같은 쓰기 API 로 올린다(`sync.ts` 의 `HttpRemote.write`, 기기 토큰). 그 내용은 기기의 `LocalVault` 가 이미 적은 것이다. 서버가 다시 덮으면 해시가 계속 어긋나 반목표 「동기화할 때마다 다시 올린다」 가 된다. 그래서 기기 토큰(서버 `Principal` 의 `device` 가 있는 소유자)으로 들어온 쓰기는 적지 않고, 그 밖의 쓰기는 늘 지금 시각으로 적는다. 「들어온 값이 지금 파일과 다르면 그대로 둔다」 는 규칙은 쓰지 않는다 — 편집기 초안에 남은 옛 시각이 되돌아와 새 시각을 덮는다.

**편집기는 적힌 시각을 받아들이지 않는다(내 결정).** 저장 응답의 내용은 보낸 내용과 `edited` 줄만 다르다. 편집기의 초안에는 옛 시각이 남지만, 다음 저장 때 쓰기 계층이 다시 지금 시각을 적으므로 파일은 늘 맞다. 받아들이려고 편집기 내용을 바꾸면 자동 저장마다 커서가 튈 수 있다. 저장 충돌의 3방향 병합에서도 한쪽(서버)만 그 줄을 바꾼 것이라 깨끗이 합쳐진다.

**프런트매터가 깨진 노트.** YAML 이 깨져 시각을 적을 수 없으면 적지 않고 그대로 저장한다 — 시각 때문에 저장이 실패하면 안 된다.

**옮기기.** 지금 이름 바꾸기·옮기기는 내용을 바꾸지 않는 연산이다(서버 `moveNode` 가 지금 내용의 해시를 그대로 넘긴다). `edited` 를 적으려면 옮기면서 내용도 고쳐야 한다.

**병합(내 결정).** 동기화의 3방향 병합(`merge3`)에서 양쪽이 `edited` 줄만 서로 다르게 바꿨으면 더 늦은 시각을 고르고 나머지를 지금처럼 합친다. 그러지 않으면 다른 문단을 고친 동시 편집이 모두 충돌 사본이 된다.

**다른 편집기.** 다른 편집기나 git 으로 바꾼 파일은 `edited` 가 갱신되지 않는다. 그때도 `edited` 가 있으면 그 값을 쓴다 — 파일 시각과 비교해 더 최근 값을 쓰면 동기화로 받은 기기에서는 늘 받은 시각이 이겨 기기마다 순서가 달라진다(내 결정).

**시각이 없는 노트.** `edited` 가 없으면 파일 시각으로 대신한다 — 서버 모드는 서버 색인의 파일 시각, 로컬 모드는 그 기기의 파일 시각. 로컬 모드에서는 동기화로 받은 시각이 기기마다 달라 그 노트들의 수정순이 기기마다 어긋날 수 있고, 그 노트를 한 번 바꾸면 그때부터 같아진다. 한꺼번에 채워 넣지 않는다(사용자 결정).

## 조회 기록(기기별)

- 기기마다 「노트 경로 → 마지막으로 연 시각」 을 저장한다(`localStorage`, `useStored` 와 같은 길). 지금의 「최근 문서」(`keyring:recent`, 볼트 전체 30개)와는 따로 둔다 — 30개로는 하위 노트가 많은 노트에서 대부분이 기록 밖으로 밀린다.
- 개수 제한 없이 두고, 지운 노트는 치우고, 이름 바꾸기·옮기기는 경로를 따라 고친다(「최근 문서」 가 하는 것과 같은 자리에서).
- 조회순이라는 **선택**은 볼트에 있지만 **기록**은 기기별이다. 같은 노트라도 기기마다 순서가 다를 수 있다 — 반목표 「열기만 했는데 파일이 바뀐다」 를 피하는 대가다.

## 화면 글과 문서

- 화면 글은 `packages/core/src/messages/{en,ko}.json` 에 영어 기준으로 둔다.
- `docs/ops/ux.md` 에 이 기능의 절을 두고, 사용자 문서 `docs/manual/en/`·`docs/manual/ko/` 의 트리 설명에 정렬 고르기·커스텀 순서 바꾸기를 더한다.

## 빌더에게 남기는 것

- rank 키의 구현과 글자 집합, 길어졌을 때 다시 고르게 펴는 처리를 할지.
- 끌어 놓기 가장자리 폭, 삽입선 모양, 단축키.
- `TreeNode` 에 실을 필드의 모양(시각을 숫자로 보낼지 등)과 서버 색인에서 읽는 비용.
- 속성 패널(`Properties`)에서 `sort`·`rank`·`edited` 를 그대로 보일지, 숨길지, 읽기 전용으로 둘지.
- 링크 고쳐 쓰기·되돌리기처럼 여러 노트를 한 번에 바꾸는 연산에서 시각을 적는 자리(연산마다인지, 쓰기 계층 한 곳인지).
