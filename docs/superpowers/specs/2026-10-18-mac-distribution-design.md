# macOS 앱 배포 설계

Oct 18, 2026 · 사용자와 정한 것과 그 이유. 구현 계획은 이 문서를 근거로 따로 쓴다.

## 왜

사용자가 Apple Developer Program 에 가입했다. 데스크톱 앱(Tauri 2, `app/`)을 **처음 보는 사람도 내려받아 경고 없이 설치하고, 이후 업데이트도 앱 안에서 받게** 하려 한다. 지금은 macOS 에서 `.app` 빌드와 실행까지만 확인됐고(`2026-10-05-plan.md` 7단계 메모), 서명·공증·배포 경로·업데이트가 모두 없다. DMG 패키징은 실패한 채 원인을 보지 않았다.

## 정한 것 (사용자)

- **대상**: 처음 보는 사람도 설치한다. 그래서 Developer ID 서명과 Apple 공증은 필수다.
- **채널**: **직접 배포**(GitHub 릴리스). Mac App Store 는 하지 않는다 — 샌드박스가 필수라 사용자가 고른 아무 폴더(Obsidian 볼트 등)·홈 아래 파일을 여는 지금 구조를 바꿔야 하고, 업데이트마다 심사를 받는다.
- **릴리스 흐름**: 버전 태그를 올리면 **GitHub Actions 가 자동으로** 빌드·서명·공증하고 GitHub 릴리스에 설치 파일을 올린다. 사람의 맥에서 손으로 빌드하지 않는다.
- **업데이트**: 설치된 앱이 실행될 때 새 버전을 찾아 **"업데이트할까요?" 를 묻고**, 누르면 자동으로 받아 바꾼다.
- **업데이트 자동 확인은 끌 수 있다.** 앱 설정에 「업데이트 자동 확인」 켜기·끄기를 둔다(기본 켜짐). 이 앱은 서버 없이 쓰는 로컬 앱이라 동기화를 켜지 않으면 밖으로 나가는 요청이 없었는데, 업데이트 확인이 실행마다 github.com 에 요청을 보내게 되기 때문이다. 끄면 실행 때 확인하지 않는다.
- **앱 식별자는 `com.develma.keyringnotes`.** 지금 `dev.keyringnotes.app` 은 `.app` 으로 끝나 macOS 번들 확장자와 겹친다는 Tauri 경고가 난다. 첫 배포 뒤에는 바꿀 수 없다(업데이트가 다른 앱으로 보이고 앱 데이터 위치가 갈린다). 바꾸면 개발용 앱의 WebView 저장소(서버 연결 설정 등)가 한 번 초기화된다. 기본 볼트(`~/Documents/Keyring Notes`)는 식별자와 무관해 그대로다.
- **서버와 앱은 버전과 릴리스를 함께 쓴다.** 제품 버전은 하나이고, `v*` 태그 하나가 앱 빌드와 GitHub 릴리스를 만든다. 서버 관리 화면의 업데이트 확인(`releases/latest`)도 같은 릴리스를 본다.
  - 버전이 적힌 곳(`app/src-tauri/tauri.conf.json`, `app/src-tauri/Cargo.toml`, 루트 `package.json` — 서버가 읽는다, `packages/core` 의 화면 표시 버전)을 하나의 원천에서 맞춘다.
  - 태그와 버전이 다르면 CI 가 실패한다.
  - 첫 배포 번호는 **`v0.8.0`**. 이미 있는 `v0.7.0` 태그는 그대로 둔다. 서버 버전도 0.5.0 에서 0.8.0 으로 뛴다.

## 코디네이터가 정한 기본값 (사용자에게 말했고 이의 없음)

- **설치 파일은 `.dmg`**. 지금 실패하는 DMG 패키징의 원인을 찾아 고치는 것이 첫 단계다.
- **유니버설 빌드**(Apple Silicon + Intel). 빌드 시간이 늘지만 받는 사람의 맥 종류를 가리지 않는다.
- **업데이트 정보는 GitHub 릴리스에 함께 올리는 파일**을 앱이 확인한다. 별도 서버를 두지 않는다.
- **비밀 값은 GitHub Actions 비밀**로 둔다: Developer ID 인증서(.p12)와 비밀번호, 공증용 자격, 업데이트 서명 키와 비밀번호. 공증 자격은 Apple ID 비밀번호 대신 **App Store Connect API 키**를 쓴다(2단계 인증·앱 암호에 묶이지 않는다).
- **공증까지 성공하면 릴리스를 바로 공개한다.** 사람이 「Publish」 를 누르는 드래프트 단계를 두지 않는다(사용자가 「태그 올리면 자동으로」 를 골랐다). 대신 서명·공증·스테이플 중 하나라도 실패하면 릴리스가 공개되지 않게 한다. 업데이트 정보 파일이 없는 릴리스가 `releases/latest` 가 되면 앱 업데이트가 조용히 멈추므로, 공개되는 릴리스에는 항상 그 파일이 있어야 한다.

## 목표

1. `v*` 태그 푸시 → macOS 러너에서 유니버설 `.app`·`.dmg` 빌드 → Developer ID 서명(hardened runtime) → 공증·스테이플 → GitHub 릴리스에 `.dmg` 와 업데이트용 파일을 올린다.
2. 받은 `.dmg` 를 처음 보는 맥에서 열어도 Gatekeeper 경고 없이 설치·실행된다.
3. 설치된 앱이 실행 때 새 릴리스를 찾아 사용자에게 묻고, 승낙하면 받아서 설치하고 다시 시작한다. 업데이트 파일은 업데이트 서명 키로 검증한다.
4. 사용자가 직접 해야 하는 일(인증서 만들기·내보내기, API 키 만들기, 업데이트 키 만들기, GitHub 비밀 등록, 버전 올리고 태그 붙이기)을 **처음부터 끝까지 따라 할 수 있는 가이드**로 남긴다.

## 하지 않는 것

- Mac App Store, Windows·iOS·Android 배포(향후 계획, `2026-10-05-plan.md` 7단계 「향후 계획」).
- 자체 업데이트 서버, 베타·채널 분리.
- 앱 기능 변경. 배포에 필요한 것(업데이트 확인 UI, 「업데이트 자동 확인」 설정, 식별자, 버전 맞추기) 말고는 손대지 않는다.

## 실패로 보는 것 (기술적으로 돌아가도)

- 비밀 값(인증서·키·비밀번호)이 저장소·로그·릴리스 산출물에 한 번이라도 남는다.
- 업데이트 서명 키를 잃으면 기존 사용자가 업데이트를 못 받는데, 그 사실과 보관 방법이 가이드에 없다.
- 공증되지 않은 빌드가 릴리스에 올라간다(공증 실패가 릴리스 실패로 이어지지 않음).
- 업데이트 확인이 사용자 동의 없이 설치를 시작한다.

## 제약

- 패키지 매니저는 pnpm, 런타임은 mise(`mise.toml`). CI 도 같은 버전을 쓴다.
- 지금 앱의 파일 접근 범위(`capabilities/default.json` 의 `$DOCUMENT`·`$APPDATA`·`$HOME`, persisted-scope)가 서명·hardened runtime 아래에서도 동작해야 한다. 필요한 entitlements 는 최소로.
- 지금 버전이 적힌 곳이 다섯이다: `app/src-tauri/tauri.conf.json` 0.7.0, `app/src-tauri/Cargo.toml` 0.7.0, 루트 `package.json` 0.5.0(서버 `APP_VERSION` 이 읽는다), `packages/core/src/i18n.ts` 의 `APP_VERSION` 0.7.0(화면 표시), 이미 있는 `v0.7.0` 태그(릴리스는 없음). 릴리스 버전과 태그가 어긋나면 업데이트 판정이 틀어진다.
- 서버 관리 화면의 "업데이트" 탭은 GitHub `releases/latest` 를 본다(`server/src/index.ts` 의 `updateUrl`). 함께 쓰기로 했으므로 앱 릴리스가 곧 서버의 새 버전이다.
- 저장소에 `.github/` 가 없다(이미지 게시 워크플로는 지웠다). GitHub 저장소는 공개이고 릴리스는 0개다.
- 지침: 커밋·문서는 한국어, README 영·한 함께, 화면 글은 `packages/core/src/messages/{en,ko}.json`, 화면 동작을 바꾸면 `docs/ops/ux.md` 도 고친다, 사람이 따라 할 절차는 `docs/guides/`(계속 쓰는 정본).

## 빌더에게 맡기는 것

- Tauri 공식 배포 방식(tauri-action 등)·환경 변수 이름·업데이터 설정 방법의 선택. 문서로 확인한 근거를 남긴다.
- DMG 실패 원인 진단과 수정 방법.
- 업데이트 확인 UI 의 모양(앱 안 대화상자, 기존 `Modal` 재사용 권장)과 확인 시점(실행 때 + 수동 "업데이트 확인" 메뉴 여부).
- CI 에서 비밀 값을 다루는 방법(임시 키체인 등)과 비밀이 로그에 안 찍히게 하는 장치.
- 서명·공증 없이도 CI 흐름을 검증하는 방법(비밀이 아직 없을 때).

- 버전의 단일 원천을 어디에 둘지와 나머지를 맞추는 방법(스크립트·CI 검사).
- 「업데이트 자동 확인」 설정을 어디에 둘지(설정 창의 어느 화면)와 저장 위치.

## 열린 것

없음. 식별자·버전·서버와의 관계·자동 확인 설정은 위 「정한 것」 에서 정했다.
