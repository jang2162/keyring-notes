# 에이전트가 하위 토큰을 발급하는 `issue` 권한 설계

## 의도

에이전트 하나가 작업을 나눠 다른 에이전트에게 맡길 수 있게 한다. 지금은 토큰을 사람(소유자)만 만든다. 맡길 때마다 사람이 관리 화면에서 에이전트를 만들고 권한을 주고 토큰을 건네야 한다.

권한 단계 맨 위에 `issue` 를 둔다. `issue` 를 가진 에이전트는 자기가 `issue` 를 가진 경로 아래로, `delete` 이하 단계만 담은 토큰을 만들어 다른 에이전트에게 건넨다.

## 목표

- 단계 순서를 `hidden < read < append < write < delete < issue` 로 한다. `issue` 는 그 경로에서 `delete` 가 하는 일을 전부 한다.
- `issue` 를 가진 에이전트(발급자)는 MCP 와 REST 로 하위 토큰을 만들고, 자기가 만든 하위 토큰을 목록 보기·재발급·삭제한다.
- 하위 토큰이 실제로 쓰는 권한은 **매 요청마다** 「자기 규칙」과 「발급자의 지금 권한(`delete` 로 깎은 것)」 중 엄한 쪽이다. 사람이 발급자의 권한을 줄이면 하위 토큰도 바로 줄고, 발급자를 지우면 하위 토큰도 함께 사라진다.
- 소유자는 관리 화면과 CLI 에서 하위 토큰을 보고(발급자 표시) 지울 수 있다.

## 하지 않는 것

- **하위 토큰은 `issue` 를 갖지 못한다.** 발급은 한 단계뿐이다. 그래서 권한을 겹치는 계산도 한 번이면 된다.
- **만료 시각은 넣지 않는다.** 발급자를 지우면 하위 토큰이 함께 막히는 것으로 갈음한다.
- **발급자는 하위 토큰의 규칙을 고치지 않는다.** 바꾸려면 지우고 다시 발급한다.

## 실패로 보는 것 (기술적으로 돌아가도)

- 발급자가 자기 `issue` 범위 밖이나 자기가 못 보는 경로를 하위 토큰으로 보게 되는 것.
- 발급자가 남의 에이전트(사람이 만든 것, 다른 발급자의 것)의 토큰을 재발급·삭제하거나 이름을 가로채는 것.
- 사람이 발급자의 권한을 줄이거나 발급자를 지웠는데 하위 토큰이 이전 권한으로 계속 쓰이는 것.

## 제약

- 토큰 원문은 저장하지 않는다. 지금처럼 sha256 해시만 둔다(`AgentConfig.tokenHash`).
- 경로 판정은 `AccessPolicy.level` 한 곳을 쓴다. 대소문자·유니코드 정규화 규칙(제한은 철자가 달라도 적용, 허용은 글자로 맞아야 넓어짐)이 발급 범위 판정에도 그대로 적용돼야 한다.
- `SCHEMA.md`·`keyring-settings.md` 를 에이전트에게 읽기 전용으로 깎는 판정(`ScopedVault.level`)은 하위 토큰에도 그대로 적용된다.
- 에이전트 이름은 서버 전체에서 하나다(`AGENT_NAME_RE`). 커밋 작성자가 에이전트 이름으로 남기 때문이다.

## 접근 방법

| 방법 | 내용 | 대가 |
| --- | --- | --- |
| **A. 하위 토큰도 보통 에이전트로 저장하고 `issuedBy` 를 붙인다 (고름)** | `AgentConfig` 에 발급자 이름을 넣는다. 인증할 때 발급자 규칙과 겹쳐 정책을 만든다 | 작성자, 마지막 사용 시각, 검토 대기열, 관리 화면, CLI 가 지금 코드 그대로 하위 토큰에 적용된다. 겹치는 정책 하나만 새로 만든다 |
| B. 발급자 항목 안에 하위 토큰 목록을 둔다 | `AgentConfig.children[]` | 계층은 구조에서 바로 보이지만 인증·작성자·관리 화면·CLI 를 한 벌씩 더 만들고 설정 형식이 바뀐다 |
| 발급 시점에 끊기 (버림) | 발급 뒤 하위 토큰은 독립 에이전트 | 단순하지만 발급자 권한을 줄여도 이미 나간 토큰이 남는다. 새어 나간 토큰을 사람이 하나씩 찾아야 한다 |

사용자가 「발급자에 계속 묶어 둔다」와 A 를 골랐다.

## 사용자가 정한 것

- 권한 이름과 자리: 상위 권한 `issue`(토큰 발급). 발급 범위는 그 경로 하위, 단계는 `delete` 이하.
- 하위 토큰의 권한은 발급자의 **지금** 권한에 계속 묶인다. 발급자가 삭제되면 하위 토큰도 무효.
- 저장 방식은 A.
- 발급자는 자기가 만든 하위 토큰만 목록 보기·재발급·삭제한다. 규칙은 고치지 않는다.
- 하위 토큰 이름은 `<발급자>-<이름>` 꼴로 강제하고, 서버 전체에서 겹치지 않는다(전체가 지금 에이전트 이름 규칙 `AGENT_NAME_RE` 에 맞아야 한다).
- 검토 대기 제안을 승인할 때 그 에이전트의 **지금** 권한(하위 토큰이면 겹친 것)으로 다시 판정한다.
- 소유자는 관리 화면에서 하위 토큰도 보고 지울 수 있고, 표에 발급자가 함께 나온다.
- 만료 시각은 넣지 않는다.

## 설계

### 데이터

`AgentConfig` 에 선택 필드 `issuedBy?: string` 을 더한다. 사람이 만든 에이전트는 이 필드가 없다.

설정 파일 검증(`validate`, 백업 복원 `replaceAll` 도 같은 길)이 거부하는 것:

- `issuedBy` 가 있는 에이전트의 규칙에 `issue` 가 있다.
- `issuedBy` 가 가리키는 에이전트가 또 `issuedBy` 를 갖는다(두 단계 발급).

`issuedBy` 가 가리키는 에이전트가 설정에 없으면 검증은 통과시키고 그 토큰은 인증에서 거부한다(아래). 손으로 고친 설정 한 줄 때문에 서버가 뜨지 않는 것보다 그 토큰만 막히는 편이 낫다.

### 권한 판정

`LEVELS` 끝에 `issue` 를 더한다. `atLeast(level, "delete")` 류의 판정은 순서 비교라 `issue` 도 그대로 통과한다.

`agentByToken` 이 하위 토큰을 찾으면 정책을 「하위 토큰 규칙의 `AccessPolicy`」와 「발급자 규칙의 `AccessPolicy`」 둘로 만들고, 경로마다 `min(자기 단계, min(발급자 단계, delete))` 를 돌려주는 정책을 `Principal.policy` 로 넘긴다. `mayContainVisible` 도 두 정책 모두 참일 때만 참이다. 발급자가 설정에 없으면 `null`(인증 실패)이다.

발급자를 찾는 것은 매 요청마다 `this.get()` 의 최신 설정에서 하므로, 사람이 발급자의 권한을 바꾸면 하위 토큰도 다음 요청부터 바뀐다.

### 발급할 때 검사

발급자가 보낸 `{ name, rules }` 를 받아:

1. 발급자 자신이 하위 토큰이면 거부(어차피 `issue` 가 없지만 명시적으로).
2. 발급자는 이름의 뒷부분만 보낸다. 서버가 `<발급자>-<이름>` 으로 붙인 전체 이름이 `AGENT_NAME_RE`(64자 제한 포함)에 맞지 않으면 거부. 접두사를 강제하는 이유: 발급자가 다른 에이전트의 이름이 있는지 알아낼 수 있는 범위를 자기 이름 아래로 좁히고, 지워진 에이전트의 이름(예: `claude`)을 하위 토큰이 다시 써서 커밋 이력의 작성자나 그 이름으로 남은 검토 제안과 섞이는 것을 막는다. 이력만 봐도 누가 발급했는지 보인다.
3. **같은 이름의 에이전트가 이미 있으면 거부한다.** 지금의 `ConfigStore.issueToken` 은 같은 이름이 있으면 그 토큰을 갈아 끼운다. 발급자가 그 길을 타면 남의 에이전트 토큰을 가로챌 수 있으므로, 발급용으로 「없을 때만 만든다」는 별도 함수를 쓴다. 사람이 우연히 `<발급자>-…` 꼴 이름의 에이전트를 만들어 둔 경우도 같은 이유로 거부된다.
4. 규칙마다 `(경로 p, 단계 L)`: `p` 가 발급자의 `issue` 규칙이 덮는 범위 안이고, `L` 이 `delete` 이하이면서 발급자가 지금 `p` 에서 가진 단계 이하여야 한다. 그래서 발급자가 `업무: issue`, `업무/x: write` 이면 하위 토큰에 `업무/x: read` 나 `업무/x: hidden` 처럼 더 좁히는 규칙은 줄 수 있고 `업무/x: delete` 는 줄 수 없다. 하나라도 어기면 아무것도 만들지 않고 어긴 경로를 오류에 담는다. (이 완화는 설계자 판단이다. 실제 권한은 어차피 겹침이 정하므로 보안상 차이는 없고, 정상 요청이 오류로 돌아오지 않게 하려는 것이다.)
5. 발급자 한 명이 만들 수 있는 하위 토큰 수에 상한을 둔다(아래 「빌더 몫」).

4 의 검사는 발급 시점의 검사일 뿐이다. 발급 뒤 실제 권한은 위 「권한 판정」의 겹침이 정한다. 예를 들어 발급자가 `업무: issue`, `업무/비밀: hidden` 이면 하위 토큰 규칙 `업무: delete` 는 발급되지만 `업무/비밀` 은 하위 토큰에도 숨겨진다.

### 발급자가 하위 토큰을 다루는 것

- 목록: 자기가 `issuedBy` 인 에이전트의 이름, 규칙, 만든 시각, 마지막 사용 시각.
- 재발급: 자기가 만든 하위 토큰만. 이전 토큰은 바로 무효.
- 삭제: 자기가 만든 하위 토큰만.

남의 이름을 주면 「없는 에이전트」와 같은 오류를 낸다(존재 여부를 흘리지 않는다).

### 발급자가 바뀔 때

- 발급자 삭제(소유자가 관리 화면이나 CLI 로): **하위 토큰도 함께 설정에서 지운다.** 화면과 CLI 는 지우기 전에 함께 지워질 하위 토큰 이름을 보여 준다.
- 발급자 토큰 재발급: 하위 토큰은 그대로 둔다. 재발급은 발급자 토큰이 새었을 때 쓰는 것이고 발급자의 정체는 그대로이기 때문이다. 새어 나간 토큰으로 하위 토큰이 만들어졌을 수 있으니, 관리 화면의 재발급 확인 문구에 하위 토큰 목록을 확인하라고 적는다.
- 발급자의 `issue` 를 거두면: 하위 토큰은 남지만 실제 권한은 겹침으로 발급자의 새 단계(최대 `delete`)를 넘지 못한다.

### 표면

- **MCP 도구** 넷: `issue_token`(`name`, `rules`), `list_issued_tokens`, `rotate_issued_token`(`name`), `revoke_issued_token`(`name`). 설명과 오류는 지금 도구처럼 에이전트 언어 설정을 따른다(`server/src/agentText.ts`). `issue_token`·`rotate_issued_token` 은 토큰 원문과 MCP 설정 예시를 이때 한 번만 돌려준다.
- **REST**: 같은 넷을 에이전트 토큰으로 부르는 `/api/*` 엔드포인트로 둔다. 바꾸는 요청은 지금처럼 `Content-Type: application/json`. 소유자(세션·기기 토큰)가 부르면 거부한다 — 소유자는 관리 API 를 쓴다.
- **`whoami`**: 에이전트가 하위 토큰이면 발급자 이름을 함께 돌려준다.
- **관리 화면(설정 → 에이전트·권한)**: 단계 고르기에 `issue` 를 더한다(하위 토큰의 행에서는 고를 수 없다). 표에 발급자를 보여 주고, 하위 토큰은 발급자 아래에 묶어 보인다. 소유자는 하위 토큰의 규칙도 고칠 수 있지만 실제 권한은 여전히 겹침이 정한다.
- **CLI**: `agent grant` 가 `issue` 를 받는다(하위 토큰에는 거부). `agent list` 가 발급자를 보여 준다. `agent remove` 는 함께 지워질 하위 토큰을 출력한다.
- **`/llms.txt`**: 발급 도구와 규칙(범위, `delete` 이하, 발급자에 묶임)을 더한다.

### 검토 대기열

하위 토큰의 쓰기도 지금처럼 검토 대상 폴더면 `pending` 이 된다. 토큰 발급 자체는 볼트 변경이 아니므로 검토를 거치지 않는다.

**승인할 때 권한을 다시 판정한다.** 지금 `ReviewQueue.approve` 는 저장해 둔 연산을 권한 확인 없이 적용한다. 바꾼 뒤에는 승인 시점의 최신 설정으로 그 제안을 낸 에이전트의 정책을 만들어(하위 토큰이면 「권한 판정」의 겹친 정책) 연산마다 필요한 단계를 다시 본다. 에이전트가 설정에 없거나(발급자와 함께 지워진 경우 포함) 단계가 모자라면 승인을 거부하고, 화면에 이유(없는 에이전트 / 권한이 모자란 경로)를 보여 준다. 소유자는 그 제안을 거절할 수 있다. 이 재판정은 사람이 만든 에이전트의 제안에도 똑같이 적용된다.

`review.ts` 에는 에이전트 이름으로 `new AccessPolicy(a.rules)` 를 만드는 자리가 있다. 이 자리도 하위 토큰이면 겹친 정책을 쓰도록, 정책을 만드는 함수를 `ConfigStore` 한 곳에 두고 `agentByToken` 과 함께 쓴다.

## 빌더 몫

- 하위 토큰 수 상한의 값(제안: 발급자당 50).
- 겹친 정책을 `AccessPolicy` 의 하위 클래스로 둘지 같은 인터페이스의 별도 클래스로 둘지.
- 소유자 `whoami` 가 보여 주는 규칙(`"/": "delete"`)을 `issue` 로 바꿀지.
- REST 엔드포인트의 경로 이름.
